# Model card: retrieval-ranking-cascade serving bundle

Format after Mitchell et al., "Model Cards for Model Reporting" (FAT* 2019). The unit of release
here is a *bundle*, not a single model: a two-tower retrieval model, an HNSW index built from its
item embeddings, a LambdaMART reranker and the feature snapshot all three depend on. They are
released together because they are only correct together — a tower trained yesterday with today's
snapshot silently changes the meaning of `tower_score`, and an index built from other embeddings
returns neighbours from a different space.

Every number below is copied from the run recorded in README.md's Results section, with the command
that produced it: Windows 10 (10.0.19045), Intel64 Family 6 Model 158 Stepping 10, 6 logical CPUs,
CPU-only, Python 3.12.14, 2026-09-27, `small` scale.

## Model details

- **Name:** `retrieval-ranking-cascade` serving bundle, schema version 1
- **Version:** identified by `bundle_id`, the SHA-256 of its own manifest. The run the numbers below
  come from is `85d421117589…`; the id is illustrative rather than reproducible, because it also
  commits to `created_at`, so two runs of the same config produce byte-identical artifacts under two
  distinct ids — two distinguishable deployments of the same model, which is what a rollback needs.
- **Owner:** Rouviere German
- **Date:** 2026-09-27
- **License:** MIT (code). The data is generated by this repo, so there is no third-party data
  license.
- **Components:**

  | Component | Type | Artifact | Format |
  |---|---|---|---|
  | User and item towers | 2-layer MLP over a learned id embedding plus side features, L2-normalized output, 32 dimensions | `tower.npz` | `.npz`, `allow_pickle=False` |
  | ANN index | faiss `IndexHNSWFlat`, inner product, M=48, efConstruction=300, default efSearch=768 | `index.faiss` | faiss serialization, SHA-256 verified |
  | Reranker | LightGBM `lambdarank`, 200 trees, 31 leaves, 10 features | `ranker.txt` | LightGBM text, SHA-256 verified |
  | Feature snapshot | user, user x category and item aggregates built with DuckDB | `snapshot.npz` | `.npz`, `allow_pickle=False` |
  | Drift reference | subsampled training distributions per feature plus embedding norms | `reference.npz` | `.npz`, `allow_pickle=False` |

- **Nothing is pickled.** `.npz` is loaded with `allow_pickle=False`, the ranker is text, and a test
  bans the pickle family from `src/` (`tests/unit/test_no_pickle.py`).
- **Run manifest:** `manifest.json` inside the bundle directory records the impression-log SHA-256,
  every seed, every hyper-parameter of the world / tower / index / ranker / snapshot, the estimated
  examination propensities, the `uv.lock` SHA-256, the installed versions of numpy, pandas, pandera,
  pydantic, faiss-cpu, LightGBM and DuckDB, a SHA-256 and byte size per artifact, and the training
  metrics. Inspect it with `uv run retrieval-ranking-cascade bundle <dir>`.

## Intended use

- **Primary use:** demonstrating and measuring a multi-stage recommendation cascade — the recall /
  latency / precision trade-offs, graceful degradation under a latency budget, and
  position-bias-corrected offline evaluation. It is a portfolio and teaching artifact.
- **Intended users:** engineers reading the repo, and its own benchmarks and tests.
- **Out-of-scope uses:** anything involving real users. The model is trained entirely on a synthetic
  world whose ground truth the repo also owns, so its parameters carry no information about any real
  catalogue, any real user or any real preference. Nothing here transfers to production data; the
  *code* might, the weights certainly do not.

## Training data

- **Source:** `src/retrieval_ranking_cascade/data/generator.py`, a seeded synthetic world. Users and
  items share a latent space built from category centres; item popularity follows a power law; 8% of
  items launch after day 0. Ground-truth relevance is
  `sigmoid(a * <p_u, q_i> / k + w * z_pop(i) + b)`. A previous production policy scores a candidate
  pool with a noisy, popularity-biased version of the true score and shows the top 10, and clicks
  follow the position-based model `P(click) = rank ** -eta * relevance` with `eta = 1.0`. A 5% slice
  of sessions shows the same slate in uniformly random order, which is what makes the propensities
  identifiable.
- **Scale used for the released numbers:** `small` — 5000 users, 10000 items, 30 categories, 200780
  impressions, a 13.9% click rate and 14054 positive pairs for the tower; the ranker trains on 3979
  label-period queries and 119370 rows. The specification's world (`full`) is 50000 users and 100000
  items. Training takes 14.7 s and the whole quality bench with ablations 123 s on six cores.
- **Fingerprint:** `manifest.json` records `data_sha256`, a content hash over the log's column names,
  dtypes, shapes and bytes. Generation is a pure function of the whole `WorldConfig`, including the
  vectorization batch size, so the batch size is part of the data's identity rather than an
  implementation detail (`tests/unit/test_generator.py::test_the_batch_size_is_part_of_the_data_identity`).
- **Contract:** `impressions_schema` and `catalog_schema` in `ml/contracts.py`, validated with
  pandera before training. A violation raises and training stops — rows are never dropped or
  quarantined, because a log that violates its own contract means the producer is broken. Failures
  are summarized as (column, check, count) only, so row values never reach the exception or the logs.
- **Splits.** Per user, sessions are ordered by day: the last is the held-out *test* session, the one
  before it the *label* session the ranker is trained on, and the rest are *history*. The tower and
  the training feature snapshot see history only; the serving snapshot adds the label period. No
  feature a ranker row uses can have been computed from the click it is trained to predict
  (`tests/integration/test_pipeline.py::test_training_features_never_see_the_label_period`).
- **Known gaps.** There is exactly one interaction type (a click), no session context, no query text,
  no price or inventory, no time-of-day effect, no user churn and no item retirement. Category
  membership is single-valued. The click model is stationary, which is the strongest simplification
  in the whole repo: real position bias varies by device, layout and intent.

## Evaluation

All of it from `uv run python bench/bench_quality.py --check --ablations` unless noted.

Two protocols, because neither alone is honest. **Slate reranking** keeps exactly the items the
logging policy showed and asks each policy to reorder them — the only question click data can answer,
since an item that was never shown has no click to be right about. **Full corpus** lets each policy
pick 10 items out of the whole catalogue and scores them against the world's true relevance — the
question that matters, answerable only because the world is synthetic.

| Metric | Value | Why it is here |
|---|---|---|
| recall@500 vs exact, efSearch 768 | **0.9771** | The ceiling on everything downstream: an item retrieval misses can never be recommended |
| Slate NDCG@10, ground truth — cascade / tower / popularity | **0.8545** / 0.8324 / 0.7442 | The cascade beats both baselines on the protocol the ranker was trained for |
| Slate NDCG@10, ground truth — logged policy | 0.8629 | Reported so the cascade is not compared against a straw man |
| Corpus NDCG@10 — cascade / tower / popularity | 0.6100 / 0.6205 / 0.3224 | Beats popularity by 0.29; **does not beat the tower** (see Caveats) |
| Corpus NDCG@10 — exact full-corpus ranking | 0.6095 | The unservable reference the cascade approximates, over the same 150 users |
| Reference retained | **1.0007** (gap -0.0004) | The cascade's own two approximations cost no measurable quality; the reference is not a ceiling |
| Per-rank relevance bias, naive / IPS | 0.2513 / **0.0373** (85.2% reduction) | Whether the bias correction works at all |
| Policy-advantage bias, naive / IPS | 0.1406 / 0.1063 (24.4% reduction) | The harder, more realistic question; a much smaller win, reported as such |
| Examination exponent, estimated / true | 1.024 / 1.0 | Recovered from the randomized slice alone |
| Intra-list similarity, MMR off / as served | 0.5128 / 0.5062 | What the diversity rules buy, at a cost of 0.0041 NDCG |
| Catalog coverage, popularity / cascade | 0.0015 / 0.0226 | A cascade is not just more accurate, it shows more of the catalogue |
| Simulated CTR (feedback simulator) | 0.1975 | Closes the serve-observe loop; an assumption, not a measurement |
| Served p50 / p99 at 50 RPS | 12.74 ms / **20.51 ms** | `bench/bench_load.py`; the 50 ms SLO, with zero errors |

**Slices.** Every corpus row, the exact full-corpus ranking included, is averaged over the same 150
sampled users, and each row reports its own user count. Cold users (at most one click in the history
period, 19 of the 150) score 0.4115 against 0.6059 overall for the served cascade, and 0.2733 against
0.3224 for popularity — the cascade's advantage over popularity is *larger* on cold users, not smaller.
Cold items (launched after day 0) make up 6.5% of the cascade's lists against 0.0% of popularity's; the
exact full-corpus ranking pushes that to 15.1%, so the candidate set is what limits cold-item exposure,
not the ranker.

**Ablations.** logQ correction on/off: recall 0.9748 / 0.9827 and corpus NDCG 0.6100 / 0.5886, so it
trades a little recall for ranking quality. Ranker labels: IPS weights 0.6100 corpus NDCG against
naive clicks 0.5690 and LightGBM's unbiased lambdarank 0.4834 — the last wins the slate metric
(0.8722) and loses the corpus metric badly, which is why it is off by default. Rerank depth: quality
peaks at 100 (0.6100 against 0.6054 at 150) while cost is linear (2.97 ms at depth 50 to 9.38 ms at
500), which is why the served default is 100 rather than the 150 this repo first shipped.

## Robustness, drift and monitoring

- **Adversarial test (shilling).** `tests/integration/test_evaluation.py::test_robust_aggregation_damps_a_shilling_attack_the_naive_one_falls_for`
  and the `robustness` block of the quality bench inject fake accounts that each click a target item
  plus popular filler — the classic bandwagon profile. Against 200 one-session accounts the robust
  aggregation keeps the target at rank 1828 of 10000 while the naive one puts it at 48; the lift is
  damped 27x. **Against 200 accounts with four sessions each the defence fails** (target rank 46,
  damping 0.58x). Thresholds in `bench/thresholds.json` enforce the one-session cases only, because
  that is what this control actually achieves.
- **Adversarial test (index corruption).** `retrieval/canary.py::corrupt_index` overwrites a fraction
  of the stored vectors with random unit vectors — the graph still returns plausible neighbours, so
  nothing raises. The canary catches it in one cycle: recall 0.9833 to 0.3642.
- **Numerical robustness.** Every analytic gradient entry is compared with a central finite
  difference over a range of shapes and both logQ settings
  (`tests/unit/test_two_tower.py::test_analytic_gradients_match_central_differences`). A tower whose
  every ReLU unit is dead produces a zero embedding and finite gradients rather than NaNs, because
  the normalization keeps epsilon inside the square root.
- **Drift monitors.** PSI per ranker feature against the bundle's stored training reference,
  threshold 0.2 (`src/retrieval_ranking_cascade/ml/drift.py`); PSI of the item embeddings'
  pre-normalization norms against the same reference, which catches a bundle swap that changed the
  tower even though the unit-norm outputs look fine. Feature rows are recomputed for every 20th
  response into a bounded ring buffer, and PSI is reported only once the buffer holds at least 200
  rows.
- **Performance monitors.** `ann_recall_canary` (alert below 0.9), `degraded_responses_total` by
  reason, `stage_latency_seconds` per stage plus a `queue` bucket, `catalog_coverage`,
  `simulated_ctr`, `feedback_events_total` and `feedback_rejected_total` by reason. The runbook for
  each alert is at the end of `docs/THREAT_MODEL.md`.
- **Reproducibility.** Two full training runs of the same config produce byte-identical artifacts and
  an identical metric hash (`tests/integration/test_pipeline.py::test_the_same_config_reproduces_the_data_hash_and_the_metric_hash`).
  That test is how a real non-determinism was found: DuckDB sums a group in whatever order its
  morsels finish in, and the popularity `argsort` turned a last-bit difference into a swapped pair of
  items. The connection is now pinned to one thread and the sort keys are rounded above the noise.
- **Retraining trigger.** In this repo, a retrain is a decision a human makes; there is no scheduler.
  The conditions that should prompt one: any `feature_psi` above 0.2 that is not explained by a
  bundle swap, a canary alert that survives a reindex, or a catalogue whose cold-item share has grown
  beyond what the snapshot's item statistics cover.

## Ethical considerations

The data is synthetic and contains no personal information, so there is no privacy risk in the
training set and no demographic group that could be over- or under-served — which also means the
repo **cannot** demonstrate fairness analysis, and its absence should not be read as a clean bill of
health for a real system.

Two properties are worth naming anyway, because they are properties of the design rather than of the
data. First, the ranker's features include item popularity, so a popularity feedback loop is
structurally possible; `catalog_coverage` and the cold-item share exist to make it visible, and the
MMR / category-cap rules push against it. Second, user ids reach the logs and the audit trail only as
keyed, truncated HMAC digests with a per-process key, so an operator reading logs cannot tie activity
back to an id or correlate across restarts. A real deployment would need a documented retention
period for the impression log, which this repo does not model.

## Caveats and recommendations

- **The reranker does not beat the tower on the full-corpus protocol** (0.6100 against 0.6205). The
  `exact_rank` row (0.6095, same 150 users) shows the limit is the model and not the cascade: scoring
  every item in the catalogue with it does not beat the tower either. The ranker is trained on the
  slates the logging policy chose, which is the only supervision click data honestly provides, and that
  distribution does not cover the catalogue. Do not read the cascade's corpus NDCG as evidence that
  LambdaMART reranking pays off at every scale — read the slate table, where it does.
- **At 10k items the ANN index is slower than brute force** (0.12x), and at 100k it is still slower
  (0.64x) for the 500 candidates this cascade asks for; the four-point fit puts the crossover near
  197k items. The same index at 100k items is 15.5x faster than brute force for a 10-neighbour query,
  so the trade is about candidate count and dimension, not about HNSW being wrong. The index is here
  for the recall knob it exposes, the canary it makes meaningful, and the catalogue sizes past that
  crossover.
- **The evaluation grades a model against a world this repo also wrote.** Ground-truth relevance is
  available because the generator owns it. That is what makes the bias measurement possible, and it
  is also the reason none of these numbers say anything about real data.
- **The simulated CTR assumes the click model.** It belongs next to the ground-truth relevance
  metrics, never on its own.
- **Propensities are identified only up to the scale of rank 1**, ranks with too little randomized
  traffic inherit the nearest reliable rank, and weights are clipped at 20 — a deliberate trade of a
  little bias for a large variance reduction.
- **Tenure-based shilling defence saturates.** See above; account-age gates and collusion detection
  are out of scope.
- **The latency numbers move with the machine's other work.** Three clean runs measured a nominal
  p99 of 18.9, 19.9 and 21.9 ms; two runs taken while the test suite was also running measured 39.7
  and 48.7 ms. Expect a different number on different hardware, which is why CI enforces the
  machine-independent invariants rather than the absolute limit.
- **The load generator, not the server, is the limit at 200 RPS on six cores.** One run in three has
  its 4x phase flagged harness-limited (client p50 51 ms against a server-side p50 of 6.4 ms), and the
  bench then declines to assert the shed-quality invariant for it. Deep-overload behaviour is
  therefore evidenced by the unit tests that drive the ladder directly rather than by the load test.
- **The budget controller bounds planned work only.** A stage that has started is never interrupted,
  so one pathological request can still overshoot.
